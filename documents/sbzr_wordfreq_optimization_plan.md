# SBZR 中文词频与候选排序优化计划

## 目标
解决“常用词在候选靠后、词频层级混乱、同词多编码排序不稳定”问题，同时保持声笔编码规则、Chrome 扩展双端同步和现有用户词频数据不被破坏。

## 当前基线（2026-08-26）
- 主方案：`sbzr.schema.yaml`，词典入口：`sbzr.dict.yaml`。
- 词库主要分布在 `sbzr.chrome.extension/dicts/`。
- 重要规模：`base` 约 54 万条；`extended.common` 约 66 万条；rimeice 3/4/5+ 字合计约 320 万条。
- rimeice 词库大量词条集中在权重 2100；extended.common 大多低于 1000；不同来源权重区间没有统一标尺。
- `lua/length_priority.lua` 当前优先按词长排序，再保持原候选顺序；这可能压过真实词频。
- `lua/dynamic_freq.lua` 已有个人选词提升机制，但当前更接近“最近选择提升”，不是累计使用次数模型。
- `adjust_weights.py` 只处理 len1，且含旧绝对路径/旧目录名，不作为正式生产流程。

## 总原则
1. **只生成新文件，不覆盖原始词库**，每个阶段保留 manifest、统计表和可回滚 patch。
2. **不改变编码真理来源**：`resource/常用字双拼拼音.db` 继续是单字主音依据。
3. **不删除候选**：频率优化只改变排序/权重；冷门词仍可检索。
4. **用户学习优先**：个人动态频率始终高于静态语料频率。
5. **公开可复现**：脚本不依赖外发私密数据；私人用户词频仅作为本地/同步层输入，不提交原始个人数据。
6. **扩展与 Rime 同步**：静态词频层如果进入 `sbzr.dict.yaml`，必须同步更新 Chrome 扩展加载清单和构建/部署说明。

## 阶段 0：基线与安全快照（必须先做）
产物：`analysis/wordfreq-baseline/`
- 记录 git commit、词库文件 SHA256、每个词库的行数/权重分布/重复 text+code 数量。
- 生成常用词探针表：至少包含“我们、这个、可以、现在、因为、所以、如果、已经、自己、没有、需要、问题、应该、设置、文件、中国”等，并记录所有编码/权重/来源。
- 生成同 text 多 code、多来源、多权重异常表。
- 生成“候选顺序影响因素”说明：schema filter 顺序、length_priority、dynamic_freq、history translator、completion。
- 当前线上/本机原词库不改；baseline 可反复执行。

## 阶段 1：修正排序算法（低风险，优先交付）
目标：避免低频短词无条件压过高频长词。
- 先写离线模拟器，用同一组候选输入比较旧规则与新规则，不立即改 Lua。
- 新规则候选：先按有效权重排序；只有权重差距在小窗口内时，才用词长作为 tie-breaker。禁止无条件 length-first。
- 明确 dynamic_freq 的插入点和优先级，确保用户实际选中的词可以稳定置顶。
- 用探针输入做回归：短词/长词、同词多编码、completion、用户已选词。
- 模拟结果满意后再修改 `lua/length_priority.lua`，保留旧版本备份，并在 Linux 本机用 Rime 可用的最小检查验证。

## 阶段 2：建立静态频率分层（不直接改巨型词库）
产物：`sbzr.chrome.extension/dicts/sbzr.common-frequency.dict.yaml` 和生成脚本/来源说明。
- 从仓库现有可靠来源中抽取高频候选，先做 500～2000 词的小层，不凭感觉全量重标。
- 对同一 text 的多个合法 code 保留，但以编码规则和主音规则标记 canonical code；不能静默删除多音编码。
- 设计独立权重区间，例如：个人动态层最高；common-frequency 次之；base/普通扩展层再次；地名/物种/诗词/长句较低。
- 频率文件必须有生成 manifest：输入来源、规则版本、生成时间、词数、权重区间。
- 先只覆盖日常高频词和用户实际报出的词，不把外部来源的整套词库直接抬高。

## 阶段 3：rimeice 与扩展词库归一化研究
- 统计 rimeice 各长度文件的重复率、同权重比例、与 base/common 的覆盖关系。
- 对“全部 2100”的来源做保守分层，不马上批量改权；先生成 dry-run 分布和候选变化报告。
- 给出三种可选策略并实测小样本：
  A. 保留来源权重，仅增加 common-frequency 覆盖层；
  B. 来源内归一化后按长度轻微惩罚；
  C. 统一 corpus score 后再叠加 source bonus。
- 选择标准：常用探针首选改善、冷门词可达、候选总数不异常膨胀、Chrome 扩展/Rime 结果一致。

## 阶段 4：个人频率闭环增强（可选，需数据确认）
- 先审计 `dynamic_freq.lua` 实际记录格式和 LevelDb 数据，不读取/提交私密原始用户数据。
- 评估从“最后一次选择”改为“累计次数 + 时间衰减”的方案：`score = count_weight + recency_decay`。
- 只在本地运行时改；提供迁移/回滚方案；同步文件保持兼容。
- 如果当前动态频率已足够，不为复杂而复杂，保留现状。

## 阶段 5：双端同步与发布
- 更新 `sbzr.dict.yaml` 导入顺序、Chrome 扩展 `shared/dicts.js` 清单（如适用）。
- `./rebuild.sh`/仓库实际 rebuild 流程生成部署产物。
- Rime 端：Linux/当前机验证 schema 编译、候选探针、用户词频不丢。
- 扩展端：启动加载、候选顺序、编辑器显示、同步按钮和现有词库清单回归。
- 只提交生成脚本、统计报告、频率层和必要 Lua/入口改动；不提交私人 userdb/动态数据库。

## 阶段 6：交付 Mac 测试包
每次可测试版本提供：
- 一个明确版本目录/commit。
- 变更文件清单与回滚命令。
- 10～20 条候选探针（输入码、预期常用词位置、实际变化原因）。
- Mac 安装/刷新 Rime 的步骤，但不自动覆盖 Mac 用户数据。
- 请用户反馈：常用词是否前移、哪些词仍靠后、是否有误置顶/候选污染。

## 验收指标
- 高频探针首选/前 3 候选改善率可量化，不能只凭截图宣称成功。
- 同词多编码不丢，编码与主音规则无回归。
- 冷门词仍可通过完整编码检索。
- Rime 与 Chrome 扩展加载同一静态词频层。
- `lua`/Python 脚本语法检查通过，生成过程可重复。
- baseline 与新版本均可一键恢复；git diff 只包含本计划相关文件。

## 当前执行批次
先执行阶段 0 + 阶段 1 的离线模拟和小范围修复；阶段 2 生成 500～2000 词覆盖层；阶段 3 只做 dry-run 对比。未经 Mac 实测反馈，不进行全量 rimeice 权重重写。
